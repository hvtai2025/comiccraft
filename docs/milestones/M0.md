## 3. Findings

### F1 — A build log under `docs/` fails the brands gate (blocking; fixed)

The first baseline run failed at `test`, reported as
`xtask::brands::tests::the_tree_is_clean`. Cause: `cargo xtask brands` scans **every
non-Markdown text file under `docs/`**, and the gate log — which the M0 procedure itself
prescribes saving to `docs/ci-baseline-<sha>.txt` — quotes upstream test names such as
`an_illustrator_ai_file_opens_from_its_editing_data` and `photoshop_filters_…`. The log was
the **only** cause; `brands` and `assets` both pass without it.

Fixed by writing gate logs as **`.md`** (Markdown is exempt from the brands scan). The fix was
applied to the procedure and to all four affected scripts (`gate.sh`, `status.sh`,
`preflight.sh`, and the M0 prompt), each with a comment saying why the extension must not
change. Confirmed: `cargo xtask brands` → `no vendor names in user-visible text`, and
`brands::tests::the_tree_is_clean` → ok.

### F2 — The toolchain is a real precondition (blocking; fixed)

`cargo metadata` fails outright on this workspace with the system Rust 1.75: *"`resolver`
setting `3` is not valid"*. The workspace declares `resolver = "3"`, `edition = "2024"` and
`rust-version = "1.95"`.

Resolved by installing rustup with stable **1.99.0** plus `clippy`, `rustfmt` and the
`wasm32-unknown-unknown` target, and adding `~/.cargo/env` to `~/.bashrc` **and** `~/.profile`
(a login shell does not read `.bashrc`). `docs/development.md:229` states the gate targets
**current stable** and that `rust-version` is only the minimum, so 1.99 is the correct choice
rather than a deviation. Clippy raised no new-lint failures, which was the main risk.

### F3 — `docs/development.md` and the workflows disagree on the toolchain

`docs/development.md:229` says the gate targets current stable with no pin; the
`affinity-corpus` workflow pins `toolchain: "1.95"`, and the other workflows use `@stable`.
Not a defect to fix, but a team should know which it is reproducing. Recorded here rather than
changed.

### Round 1 found a real bug in the implementer's test suite

Round 1 ran a mutation experiment. Mutating `overlaps` from `<` to `<=` on the **y axis only**
left the implementer's suite green while reporting every vertically stacked pair of panels as
overlapping — the original test only used side-by-side rectangles, so it exercised one axis.
Round 1 also found that `PanelRect::new` documented an invariant it could not enforce: the four
fields were `pub` and `Deserialize` was derived, so two paths built a `PanelRect` without
consulting the constructor.

All five findings were fixed. Making the invariant real required private fields and removing
`Deserialize` (`PanelRect` is a layout primitive, not a wire type — schema §6.2 gives `Panel`
no geometry). The strengthened test then exposed a second defect the original suite could not
have found: at `x = f64::MAX / 4.0`, `x + 1.0 == x`, so the rectangle had zero area and **failed
to overlap itself**, which would have made the validator's overlap check unsound. `new` now
rejects a size too small to advance the far edge.

### Round 2 verified the fixes rather than the summary

- Attempted the four remaining construction bypasses and **compiled** them, recording `E0616`,
  `E0277` (`Default`), `E0277` (`Deserialize`) and the absence of `From`, a `serde` attribute,
  a `pub` field and `unsafe`. The round-1 reproduction is now a compile error.
- Re-ran the y-axis mutation that exposed the first bug: **now caught** by four tests.
- Verified the new guard is exact, not ULP-approximated, over an 18×10 grid per axis.
- Reported one of its **own** tests that survived a mutation, fixed it, and re-confirmed.

**59 tests pass.** Round 2 returned three preferences and no bugs; all three are recorded in the
review record as tracked follow-ups rather than fixed, because changing production code would
invalidate the approval and require a third round. The lead does not fully accept one of them —
`PanelRect::new(f64::MAX, 0.0, f64::MAX, 10.0)` is accepted because `MAX + MAX` overflows to
`+∞`, and `contains` on such a rectangle returns `true` for everything — so it is tracked as
`PANELRECT-OVERFLOW` for M1 with the fix sketched.

### The model requirement was enforced

Both rounds flagged that they could not confirm their own model and marked themselves *not
performed as specified* rather than guessing — the behaviour the role demands. The harness
metadata recorded `opencodego/space-bunny` for both, which is the external evidence a reviewer
cannot obtain from inside the session, so both are accepted without a waiver and the flag is
left in the record verbatim.

## 4a. The M1 hand-proof (porting plan §6 task 3) — **passed**

Driven entirely through commands, headless, via `vectorcraft-cli run`. Nothing was done by hand
in the GUI. The sequence:

```sh
vectorcraft-cli run \
  -c artboard.new      -p '{"x":0,"y":0,"width":612,"height":792,"name":"Page 1"}' \
  -c file.place        -p '{"path":"/tmp/q.png"}' \
  -c object.cropImage  -p '{"rect":[274,364,32,32]}' \
  -c object.maskImage  -p '{}' \
  -c text.create       -p '{"x":60,"y":700,"text":"The hand-proof: …","size":14,"area":{"width":300,"height":60}}' \
  -c document.serialize -p '{"format":"vectorcraft"}' \
  -c document.export   -p '{"path":"/tmp/proof-page.png","format":"png","artboards":[1]}' \
  -c document.exportPdf -p '{"path":"/tmp/proof-book.pdf"}'
```

Every step succeeded, with no warnings:

| Step | Result |
|---|---|
| `artboard.new` | `{index: 1}` — a fresh headless document already has one artboard |
| `file.place` | `{format:"png", width:64, height:64, ids:[2], linked:true, warnings:[]}` — **linked by default**, exercising `LinkInfo` |
| `object.cropImage` | `{id:2, width:32, height:32}` |
| `object.maskImage` | `{id:4, path:3}` — clip group and clipping path, as audit §6 claims |
| `text.create` | `{id:5}` — area type, frame 300×60 |
| `document.serialize` | `{dataBase64:…, warnings:[]}` |
| `document.export` | PNG, 5 264 bytes |
| `document.exportPdf` | PDF, 12 803 bytes |

### The audit's claims, verified rather than assumed

**§7 rendering.** The exported PNG is **612×792 RGBA** — the artboard at 72 ppi, exactly.

**§9 PDF page geometry.** With `bleed: 9` and `marks: {trim, registration}`:

```text
Pages:      2                       (one per artboard — the audit's claim)
TrimBox:    27.25 27.25 639.25 819.25   → 612 × 792 = the artboard
BleedBox:   18.25 18.25 648.25 828.25   → grown by 9 pt per side
MediaBox:   0     0     666.50 846.50   → enlarged for the printer's marks
```

That is precisely what audit §9 states: one page per artboard, the trim box equal to the
artboard, the bleed box grown by the bleed, the media box including marks.

**§8 typography.** The PDF carries a real **Type0 `OIVNMO+SourceSans3-Regular` Identity-H**
embedded subset — real text, not outlined glyphs. `mutool` also reports the image as
**`[Flate] 32×32 8bpc DevRGB`**, so the crop survived into the PDF.

**Crop correctness, at the pixel level.** The crop to document rect `[274,364,32,32]` kept the
source's **red** top-left quadrant and dropped the other two: inside the rect `(220,30,30)`, and
immediately right of it and below it fully transparent. Area type measured **714 ink pixels
across 13 rows** (3.2 % of the band) — glyph strokes, not a filled block.

**§5 persistence.** The saved file is `format: "vectorcraft"`, `version: 4`, with
`File.images = {crop-2: 296 bytes}` held **inline** — under the 8 KB `INLINE_MAX`, so no blob
section was needed. Save → open → save preserves everything:

```text
ids pass 1: [(1,'layer'), (4,'group+clip'), (3,'path+clipping'), (2,'image 32x32'), (5,'text')]
ids pass 2: [(1,'layer'), (4,'group+clip'), (3,'path+clipping'), (2,'image 32x32'), (5,'text')]
image blobs: ['crop-2'] -> ['crop-2']        artboards: [(1,…),(2,…)] -> [(1,…),(2,…)]
```

and the reopened document **renders byte-identical pixels** to the original.

### Findings — documentation gaps, not defects

Nothing contradicted the audit's capability claims. Five things cost time or are inconsistent
in the documentation, and are recorded as findings because the M0 prompt says a difference is a
finding, not a failure:

| # | Finding |
|---|---|
| H1 | **`object.cropImage`'s `rect` is in document space, not image-local**, and the parameter doc does not say so. `rect:[0,0,32,32]` fails with *"crop rectangle doesn't overlap the image"* on an image centred at (306,396). One cycle was lost to this; the doc should name the coordinate space |
| H2 | **`object.cropImage {}` — the documented default, "to the artboard it sits on" — errors** with *"nothing to crop"* when the image is already inside the artboard, while the `trim` path documents the analogous case as a success (`trimmed: false`). The two defaults behave inconsistently |
| H3 | **`document.exportPdf`'s `bleed` takes a struct**, not a number: `{use_document, top, bottom, left, right}`. `bleed: 9` fails with *"invalid type: integer, expected struct BleedSettings"*, and the parameter summary does not show the shape |
| H4 | **`document.inspect`'s tree shape differs from the saved JSON's** (`kind.type` / `kind.children` in the file). Not a defect, but it cost two attempts to read; the inspect schema is undocumented |
| H5 | **A fresh headless document already contains one artboard**, so `artboard.new` returns `index: 1` and a default `artboards: all` export produces two pages. Expected, but surprising when scripting |

H1 and H3 are worth fixing upstream as parameter-documentation changes; H2 is a small behaviour
inconsistency. None blocks M1.

## 4b. The comic-style foundation (ADR-017)

ComicCraft cannot look like a comic without comic lettering, and the rule is absolute: fonts live
in `storytold/craft-fonts` and **never** in this repository (`AGENTS.md`). So the work split in
two.

### In `craft-fonts`

Added the two faces the design now names, following that repo's own workflow exactly ("add the
file, its licence, a manifest line and an attribution row, and the tests check it"):

| Face | Styles | For |
|---|---|---|
| **Comic Neue** | Regular, Bold, Italic | dialogue, captions, narration |
| **Bangers** | Regular | sound effects, titles, cover text |

Both OFL-1.1, used unmodified, pinned to `google/fonts` commits with SHA-256 and licence files,
and listed in README, `ATTRIBUTION.md` and `fonts/manifest.txt`. `cargo test` in `craft-fonts` —
**8 passed, 0 failed**, including `every_file_matches_its_manifest_checksum`,
`every_font_ships_its_licence` and `every_font_is_the_family_the_manifest_says`.

### In ComicCraft

**The fonts were embedded but unreachable.** With `CRAFT_FONTS_DIR` set the build correctly
embedded them — `strings target/debug/vectorcraft-cli` showed Comic Neue and its OFL text — but
`text.fontList` did not list them, because every consumer of `CRAFT_FONTS` filters to
Japanese/Arabic faces (`craft_fonts::document_fonts()`), and a Latin-only face is in neither.
Embedded, invisible, and it would have looked like it worked.

Fixed by adding `craft_fonts::comic_fonts()` and chaining it into `FontDb::new()` after
`document_fonts()`. Three tests cover it; the important one asserts the bundled Latin family is
still what ordinary text resolves to, so comic lettering is opt-in by name and changes no
existing document.

`docs/comiccraft-design.md` records this as **ADR-017**, §8.3 names the faces, risk **R1 is
closed**, and `docs/comiccraft-project-schema.md` §5.3 names them as *defaults* — names, not
bundled files, so a project can choose differently and a build without `CRAFT_FONTS_DIR` still
loads (it reports a missing font instead of failing).

### A finding about `craft-fonts` itself

The public checkout is **incomplete** for this project. `crates/text/web-fonts.txt` lists ~30
Arabic faces (Cairo, Tajawal, Almarai, IBM Plex Sans Arabic, Noto Kufi, Amiri, Alexandria,
Fustat, Reem Kufi, Aref Ruqaa, Gulzar) that its `fonts/manifest.txt` does not have, and the
build warns about each. With `CRAFT_FONTS_DIR` pointing at it, **three `tests_bidi` Arabic tests
fail** — verified on the pristine crate with my changes stashed, so it is not caused by this
work:

| Tree | `CRAFT_FONTS_DIR` | bidi tests |
|---|---|---|
| pristine | set | **3 failed** |
| pristine | unset | all passed |

The gate is unaffected because it runs with `CRAFT_FONTS_DIR` unset, which `AGENTS.md` requires
anyway. But the release craft-fonts is clearly not this public one, and that gap should be
resolved before anyone relies on `CRAFT_FONTS_DIR` locally.
