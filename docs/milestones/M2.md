# M2 — First-class panel and lettering tools

Ported from `comiccraft-porting-plan.md` §8 (Phase 2) and §15's M2 row. **Exit criteria are quoted
verbatim below and are the definition of done.**

## 1. Exit criteria

> **Exit criteria:** panels can be created from templates, reordered and resized with validation
> warnings; every lettering kind renders, wraps, detects overflow and applies its policy; moving a
> balloon preserves or updates its tail without detaching it; and reading order is explicit, editable
> and validated independently of panel coordinates. Lettering tests pass with `CRAFT_FONTS` empty.
> **Gate:** `cargo xtask ci`, plus golden-render tests for one representative page.

So M2 has **six** criteria, and two of them are new *kinds* of evidence rather than new features:

| # | Criterion | State coming into M2 |
|---|---|---|
| 1 | Panels from templates, reordered and resized, with validation warnings | Built in M1 (W2 + `comic.page.template.apply`, `comic.panel.move/resize`); needs hardening and a **shift** test |
| 2 | Every lettering kind renders, wraps, detects overflow, applies its policy | Built in M1 (W3); needs verification at the exit criteria's own wording |
| 3 | Moving a balloon preserves or updates its tail **without detaching it** | Partial — `moved_by` exists and is tested; the criterion is about a **move**, and needs a test that says so |
| 4 | Reading order explicit, editable, validated independently of coordinates | Built in M1; **the "independently of coordinates" half needs a test that would fail if coordinates leaked in** |
| 5 | **Lettering tests pass with `CRAFT_FONTS` empty** | M1 verified this at **record** level only |
| 6 | **Golden-render tests for one representative page** | Does not exist |

## 2. What M2 does *not* need

The plan is explicit, and I am holding it to that:

- **Custom/irregular panel shapes are an extension, not a prerequisite** (§8). Frames are already ordinary
  paths, so shapes *work*; templates stay rectangular.
- **AI-assisted layout suggestions** come only *after* the deterministic engine works (§8.1). M2 is the
  deterministic engine, and the validator must remain the gate.
- **No story, character, asset or job work** — that is M3–M5.
- **No comic UI panels.** `crates/ui-egui/src/panels/comic/**` is M6. "Panel locking **and selection**"
  (§8) splits here: *locking* is persisted model state and belongs in M2; **selection is session state
  and is M6's**, and must not be written into the bundle.
- **No rendering capability.** As in M1, every pixel is produced by code that predates the milestone.

   reports the field's wire name and the v2 fixture hash the moment they are in, which unblocks W3.
2. **W2 in parallel with W1** — different tree, and it is the criterion most likely to need iteration.
3. **W4, W5 in parallel** with W1/W2 — disjoint module trees, no dependency on the new field.

## 4. The three things that are genuinely new

Everything else in M2 is *hardening what M1 built*. These are not, and each carries a risk.

### 4.1 Golden-render tests, and the font trap

**This is the riskiest item, and it has a wrong first answer.** A golden render is a pixel comparison,
and M2's other new criterion says lettering must pass with **`CRAFT_FONTS` empty** — but comic faces live
in `storytold/craft-fonts`, so **the pixels depend on whether that checkout is present**. A golden
captured with fonts and compared without them will fail for a reason that is not a defect, and a golden
tolerance wide enough to hide that would hide real regressions too.

The tooling exists (`testkit::raster::{render_artboard, assert_similar(a, b, tol, max_bad_fraction)}`) and
has never been used by a comic test. **Requirements for W2:**

- The representative page must be chosen so its pixels **do not depend on a comic face** — panels,
  gutters, frames, borders and a balloon *outline* are geometry; the text inside is not. Render geometry,
  and assert text separately at record level (as M1 does).
- If any part of the golden *is* font-dependent, it must **skip with an explicit reason naming the missing
  font**, never pass silently and never fail as though the code were wrong. A test that cannot run is not
  a test that passed.
- The tolerance and `max_bad_fraction` must be **justified in the test**, with the value that a plausible
  wrong implementation still fails. `M-CLAMP`'s lesson from M1 applies directly: ask *"could a wrong
  implementation satisfy this test?"*, and demonstrate the answer with a mutation.
- **The golden file must be reviewable** — a PNG plus the command that regenerates it, not a blob.

### 4.2 Panel locking needs a schema change against a frozen v1

**Panel locking does not exist.** I checked rather than assumed: `Panel` has `id`, `page_id`,
`artboard_id` and the rest, but **no `locked` field**, and *every* occurrence of "lock" in both the schema
and `comic-model` is about **lockout** — the §14 semantics that a damaged bundle must stay openable and
repairable. Nothing anywhere persists a locked panel.

So §8's "panel locking" requires **v2**. The machinery is designed and unexercised: `manifest.schema_version`
starts at `1`, readers accept ≤ theirs and migrate forward, and refuse greater (§11). **M1's record already
predicted exactly this** — *"§11.1 lands a v2 fixture with the field that needs it"* — so this is the
predicted moment, not a surprise.

**Scope for W1 — deliberately minimal:**
- one field, on `Panel` alone;
- a **v1 → v2 migration** that is genuinely exercised (a v1 fixture loads and gains the field's default);
- a **v2 fixture**, and the rule set updated only where a new rule is actually needed;
- **no other field rides along.** A schema bump is a budget; spending it on one field keeps the diff small
  and the migration testable. If another field is genuinely needed, it is a separate decision, not a free
  addition.

**And a v2 that cannot be *proved* to migrate is worse than no v2:** the migration must have a
failing-then-passing test in the sense §5.3.1's exit criterion uses — a v1 bundle read by v2 code, with the
v1 fixture checked in and byte-stable.

### 4.3 `CRAFT_FONTS` empty must be a *tested* contract, not a habit

M1's suites pass with `CRAFT_FONTS` empty because the environment has no fonts. That is **not** the same as
having tested the empty case: nothing asserts *what happens* when a lettering face is missing, and design
§8.3 requires a project whose lettering font is missing to **surface the missing-font report the exporter
already produces** — not to fall back silently, and not to fail to render.

W4 must make this an explicit, named contract with a test that would fail if the code silently substituted
a face. The distinction is the whole point: **a fallback that renders is exactly the failure mode**, because
the creator gets a page that looks wrong and no message.

## 5. Risk to watch

| Risk | Why it bites | Mitigation |
|---|---|---|
| **A golden that cannot fail** | Pixel tolerance is easy to widen until it certifies nothing | W2 must show a mutation the golden rejects, and justify its numbers |
| **A v2 migration that is never exercised** | v1 is the only format any fixture has ever been; the path is untested code | W1 ships a real v1 fixture and a load-it-with-v2 test |
| **`locked` honoured in some commands and not others** | The §11.1 class of defect: a policy stated in one place, applied in three of five | W3 enumerates every command that moves, resizes or deletes a panel and states the lock's effect on each |
| **Selection leaking into the bundle** | Session state in a durable file is unrecoverable later | M2 writes no selection; M6 owns it |
| **M1's `CRAFT_FONTS`-empty record-level verification being mistaken for the real thing** | It is the exact shape of every defect in M1 — a guarantee asserted, not delivered | W4's contract test names the missing face |

## 7. Findings

Recorded as they arise, with M0/M1's distinction: a **defect** (contradiction, wrong predicate, security
hole, something that would produce wrong code) blocks; a **note** does not.

### M2-F0 — the plan's §8 bullet list and its own exit criteria disagree, and the exit criteria win

`§8` lists *"Panel locking and selection"* under **Panel engine: Implement**, but neither appears in §8's
own exit criteria, and `§15`'s M2 row names only *"Panel engine, templates, gutters, lettering policy,
reading order"*. The kickoff rule is that exit criteria are the definition of done and are not to be
substituted.

**Resolution:** locking is **kept** in M2 despite not being a criterion, because it needs a **schema
change** and deferring schema changes is how a frozen format drifts; selection is **excluded** because it
is session state and belongs with the UI in M6. Both halves are recorded here so the choice is visible
rather than silent. §8.1's *"panel importance or intended emphasis"* and *"optional fixed panel geometry"*
are **deferred** — they are inputs to a layout feature no criterion requires, they have no field, and the
plan puts AI-assisted layout after the deterministic engine.
