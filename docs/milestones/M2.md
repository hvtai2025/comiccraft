## 2. What M2 does *not* need

The plan is explicit, and I am holding it to that:

- **Custom/irregular panel shapes are an extension, not a prerequisite** (§8). Frames are already ordinary
  paths, so shapes *work*; templates stay rectangular.
- **AI-assisted layout suggestions** come only *after* the deterministic engine works (§8.1). M2 is the
  deterministic engine, and the validator must remain the gate.
- **No story, character, asset or job work** — that is M3–M5.
- **No comic UI panels.** `crates/ui-egui/src/panels/comic/**` is M6. "Panel locking **and selection**"
  (§8) splits here: *locking* is persisted model state and belongs in M2; **selection is session state
  and is M6's**, and must not be written into the bundle.
- **No rendering capability.** As in M1, every pixel is produced by code that predates the milestone.

## 4. The three things that are genuinely new

Everything else in M2 is *hardening what M1 built*. These are not, and each carries a risk.

### 4.1 Golden-render tests, and the font trap

**This is the riskiest item, and it has a wrong first answer.** A golden render is a pixel comparison,
and M2's other new criterion says lettering must pass with **`CRAFT_FONTS` empty** — but comic faces live
in `storytold/craft-fonts`, so **the pixels depend on whether that checkout is present**. A golden
captured with fonts and compared without them will fail for a reason that is not a defect, and a golden
tolerance wide enough to hide that would hide real regressions too.

The tooling exists (`testkit::raster::{render_artboard, assert_similar(a, b, tol, max_bad_fraction)}`) and
has never been used by a comic test. **Requirements for W2:**

- **The representative page must contain no lettering at all — and this corrects what this section first said.**
  I originally wrote *"panels, gutters, frames, borders and a balloon **outline** are geometry; the text
  inside is not"*. **A balloon outline is not font-independent either**, and W2 proved it while
  implementing this: `crates/comic-layout/src/fit/sizing.rs` is built on `measure(…)` throughout, so the
  balloon **box** is derived from measuring the text, and the same words at 12pt and 24pt give different
  frame bounds (`the_balloon_box_is_measured_text…` pins it). A lettered page therefore **cannot** be a
  font-independent golden. The page must hold no type at all, and the test must **assert that** rather
  than trust it — W2's `the_golden_page_renders_no_text…` walks the document and fails if a text object
  ever appears, so the golden **cannot silently become font-dependent**.
  Assert text at **record** level, where M1 already does.
- If any part of the golden *is* font-dependent, it must **skip with an explicit reason naming the missing
  face** — never pass silently, and never fail as though the code were wrong. **A test that cannot run is
  not a test that passed.** The skip must also refuse to **write** a reference, even under the
  regeneration flag, or the first run in a fontless environment would bake in the wrong golden.
- The tolerance and `max_bad_fraction` must be **justified in the test**, with the value that a plausible
  wrong implementation still fails. `M-CLAMP`'s lesson from M1 applies directly: ask *"could a wrong
  implementation satisfy this test?"*, and demonstrate the answer with a mutation.
- **The golden file must be reviewable** — a PNG plus the command that regenerates it, not a blob.

### 4.2 Panel locking needs a schema change against a frozen v1

**Panel locking does not exist.** I checked rather than assumed: `Panel` has `id`, `page_id`,
`artboard_id` and the rest, but **no `locked` field**, and *every* occurrence of "lock" in both the schema
and `comic-model` is about **lockout** — the §14 semantics that a damaged bundle must stay openable and
repairable. Nothing anywhere persists a locked panel.

So §8's "panel locking" requires **v2**. The machinery is designed and unexercised: `manifest.schema_version`
starts at `1`, readers accept ≤ theirs and migrate forward, and refuse greater (§11). **M1's record already
predicted exactly this** — *"§11.1 lands a v2 fixture with the field that needs it"* — so this is the
predicted moment, not a surprise.

**Scope for W1 — deliberately minimal:**
- one field, on `Panel` alone;
- a **v1 → v2 migration** that is genuinely exercised (a v1 fixture loads and gains the field's default);
- a **v2 fixture**, and the rule set updated only where a new rule is actually needed;
- **no other field rides along.** A schema bump is a budget; spending it on one field keeps the diff small
  and the migration testable. If another field is genuinely needed, it is a separate decision, not a free
  addition.

**And a v2 that cannot be *proved* to migrate is worse than no v2:** the migration must have a
failing-then-passing test in the sense §5.3.1's exit criterion uses — a v1 bundle read by v2 code, with the
v1 fixture checked in and byte-stable.

### 4.3 `CRAFT_FONTS` empty must be a *tested* contract, not a habit

M1's suites pass with `CRAFT_FONTS` empty because the environment has no fonts. That is **not** the same as
having tested the empty case: nothing asserts *what happens* when a lettering face is missing, and design
§8.3 requires a project whose lettering font is missing to **surface the missing-font report the exporter
already produces** — not to fall back silently, and not to fail to render.

W4 must make this an explicit, named contract with a test that would fail if the code silently substituted
a face. The distinction is the whole point: **a fallback that renders is exactly the failure mode**, because
the creator gets a page that looks wrong and no message.

### 7.1 W5 — layout hard cases — landed

`layout-engineer`. **315 tests green in `vectorcraft-comic-layout`; no source file changed** — the
deliverable is `tests/m2_panel_cycle.rs` and `tests/m2_reading_order_independence.rs`. Report:
`docs/reviews/M2-layout-engineer-hard-cases.md`.

**Criterion 1 is now tested as a *cycle*, not as steps.** Apply `Grid{2,2}` → reorder to `[11,12,9,10]`
→ resize −10pt → resize +10pt → resize out-of-margin → resize undersized → reload through
`validate::page`, asserting at each step both **what must be reported and what must not**:

| step | must report |
|---|---|
| apply, reorder, resize −10pt (gutter 12→22pt) | **nothing** |
| resize +10pt (gutter 12→**2pt**, minimum 6) | one warning, naming `Page.panels[0]` and the 2pt gap |
| resize the left edge outside the 18pt margin | one warning — the safe-margin case, which for a deliberate bleed must be *confirmable* rather than silent |
| resize to 40×40pt | one **error**, below the 48×48pt minimum |
| reload via `validate::page` | **the same single warning**, relabelled `Panel(9)` |

Every premise is **measured from the rectangles** before the validator is asked, so the test cannot pass
by agreeing with itself.

**Criterion 4 is tested for the derivation, not the result** — which is the whole difficulty. Four
rectangles in *identical* positions grouped three ways give three different orders, and the test writes
the **coordinate-derived** order into the file and asserts the crate says something else; it also asserts
that on real template geometry the two readings **agree**, which is *why* a template-only test proves
nothing. Then the converse: perfect left-to-right geometry with an order that forgets a panel, or two
panels claiming each other's indices, is **reported**; the same geometry with a consistent order is
**clean**.

##### The mutations, and the standard they meet

| wrong implementation | W5's tests | everything else |
|---|---|---|
| **M-COORD** — derive the order from the rectangles (sort by `(y,x)`, reverse per `rtl`) | **rejects it** | **all green** — 176 lib + 122 crate + **1779 engine tests / 23 targets** |
| **M-AGREE** — `validate::page` requires the declared order to match the geometric order | **rejects it (4/5)** | **all green** |
| M-NOPOS — permutation checked, per-panel index not | rejects it | **not** green: 2 lib + 2 `round1_reviewer` tests already catch it — recorded as the honest negative |

**M-COORD is the M-CLAMP result: exactly one test in the entire workspace rejects deriving reading order
from coordinates**, which is the thing criterion 4 exists to forbid. And two earlier drafts of M-AGREE
were **discarded because they were caught by *unrelated* M1 tests** — as W5 put it, *"a mutant caught for
the wrong reason is not evidence."* That is a distinction I had not asked for and will carry into the
other reviewers' briefs.

### 7.2 M2-L1 — a protocol defect across the crate boundary (for W3)

**Reported by W5 from reading, not driving** — explicitly, and correctly labelled as such.

`crates/engine/src/cmd/comic/panel.rs:218-222` (`geometry_findings`, used by `comic.panel.add` and
`comic.panel.resize`) and `crates/engine/src/cmd/comic/page.rs:573-578` (`comic.page.template.apply`)
label this crate's geometry faults **`Panel[i]`** — an index into the page file's panel vector — while
`validate::page` labels the same faults **`Panel(<id>)`** (`validate/mod.rs:403-409`).

Two consequences, and the second is the serious one:

1. A resize response saying *"sits 2pt from `Panel[1]`"* **cannot be resolved to a panel id from the
   response alone**, so a caller has to hold the and index it.
2. `validate`'s own doc states that these subjects are **"this crate's own, so nothing else produces
   them"**, and offers **`(rule, subject)` as the dedupe key** for callers running both `comic-model`'s
   validator and this crate's. **With two different subject spellings for the same fault, that dedupe
   silently double-reports** — a documented contract the code breaks, which is the same shape as every
   defect M1 produced.

It is W3's tree, so it is W3's to fix, and it is a **blocking** defect rather than a note: the fix is to
make the command layer spell subjects the way `validate` does. Whether the index form has a legitimate
use in a *response* (where the caller has the file in hand) is a separate question worth one sentence in
the fix's report.

### 7.3 W4 — the face contract and the move — landed

`lettering-engineer`. **314 tests green** (M1's 289 + its 16 integration + 4 inline + W5's 5).
Production diff **3 files, +146/−10**. Report:
`docs/reviews/M2-lettering-engineer-font-contract.md`.

**Criterion 5 became a name, not a habit.** `lettering::fonts::lettering_face_report(db, faces, subject)`
is now the single route by which the face half of a plan's report is produced, and `ruler_findings`
calls it and nothing else. In **the gate configuration the six kinds produce exactly four reports**
(`Bangers Regular → Source Sans 3 Regular`, `Comic Neue Bold → …Bold`, `…Italic`, `…Regular`); with
craft-fonts present, **0**. Measured with a probe, then the probe deleted.

**It fixed a test that was quietly asserting nothing.** The previous guard was
`assert_eq!(reported, !comic_neue_available)` — which in a **fonts-present** build asserts nothing about
absence at all, so the silent-substitute case was unguarded in exactly the configuration where a
substitute would be *possible*. The replacement asks for `No Such Lettering Face Bold`, **impossible in
either configuration**, so the test is **not conditional**, and it asserts the named finding (requested
family **and** style, the status, the substitute) through both entry points **while the layout still
runs** — `fits()`, closed frame, positive finite bounds, tail intact. So it cannot pass by refusing to
lay out. Mutations **A** (report dropped — the silent fallback, which is the failure mode) and **B** (the
substitute face reported instead) each red it.

**Criterion 3 — mutation C is the M-CLAMP result again.** The move is `LetteringPlan::moved_by(delta)`,
drag semantics. For each of the four spoken kinds the test asserts the **tip is preserved exactly** (the
speaker does not move), the **base is updated** to `attach_point(&moved.frame, tip, moved.bounds)`, the
tail is attached to **the path the plan carries** *and* to the balloon, is **not left behind** on the old
frame (move = 700×500pt), and the frame is translated rather than rebuilt. The discriminating case swaps
the plan's frame for a box outline and asserts the tail rides the **path**, not the box's ellipse — and
**mutation C (re-base on the box) is caught by nothing else in the tree**: 176 inline tests and the
reviewer's 31 stay green.

**Criterion 2 is 6 kinds × 3 policies = 18 cells**, plus the collision rule (6 cells → `Blocked`, bounds
unchanged), plus a measured wrap check with the engine's between-character breaking allowed for. **Every
cell is record-level, and the file says so** — wrapping and overflow are read back from
`vectorcraft_text` (`overflow`, `lines`, `fit_scale`, `bounds`), and the pixel half is criterion 6's
golden render. Stating that in the file is the right call: it is the difference between a scoped claim
and an implied one.

**It also verified both configurations**: with `CRAFT_FONTS_DIR=<craft-fonts>` and a throwaway target
dir, all 20 new tests stay green — so none of them is configuration-dependent — and the tree was left in
the gate's empty configuration.

### 7.4 M2-L2 — `default_lettering_style` was read by nothing (W4's D1) — **fixed, and I verified it applies**

Design §8.3 says ComicCraft names the faces as **defaults in `ProjectSettings.default_lettering_style`
"rather than hard-coding them, so a project can choose different faces"**. W4 found that the field is
**read by nothing** in `crates/` or `apps/` — every occurrence outside the schema is `None` — so a
project's chosen lettering face is **never applied**, and criterion 5's report is always about the
*kind's* face. The half of §8.3's sentence about **a project's own** missing font is therefore
**unreachable**.

This is the same species as M2-L1 and every M1 defect: **a documented capability with no reader.** It is
also a schema-shaped decision — the field exists and is frozen in v1, so the fix is a *reader*, not a
field. Ownership is genuinely split (the field is the schema owner's, applying it is the lettering
engineer's, setting it is the command engineer's), so **the lead owns the split** and it is recorded here
rather than assigned silently.

##### Verified after the fact, because "a reader exists" is not the same as "it applies"

I checked this one myself rather than accepting W3's summary, and the distinction is the same one that caught
`default_template`: **a reader that nothing calls is not a fix.** It is a real fix here —
`project_face` reads the setting, `style_for_project` substitutes the family into the kind's style, and that
style goes into the plan request — so a project's chosen face **reaches the plan**, the record's
`text_layout_settings.font` and the missing-face report. And the scope is stated rather than implied: the
name is read as the **family**, while Regular/Bold/Italic stays the kind's, *"because a single string cannot
carry a pair — a project that wants a different weight per kind says so on the record with
`comic.lettering.set_style`"*. That is the right granularity to stop at, and it is written down.

**M2-L3 — a message asserting a cause that is not always true (W4's D2).** `missing_face_finding`
claims *"CRAFT_FONTS being empty is why they are looked for there"*, which is **false whenever the
missing face is not a comic face**. A message that explains a cause it has not checked is how a creator
is sent to the wrong fix.

### 7.5 W1 — schema v2 and the lock — landed, gate green

`schema-architect`. **`cargo xtask ci` passed all 7 steps.** `comic-model` **151 passed** (M1's 135
intact) plus one `#[ignore]`d fixture generator. Report: `docs/reviews/M2-schema-architect-locking.md`.

**The field**: `locked`, `bool`, default `false`, always written, documented in schema **§6.2**'s `Panel`
table with the rationale in **§5.6**'s delta table — and it is worth noting *why* it is documented there:
neither the porting plan nor design §5.2 places a field, so the schema owner had to choose a home and say
so rather than leaving it to be inferred from the code.

**No new referential rule — confirmed, and pinned.** §13 stays at eighteen. The reasoning is that locking
is not a reference, an id, a declared agreement, a path or a lifecycle; it constrains **commands**, not
**bundle legality**. A test asserts the document gives the field no rule, so symmetry cannot add one
later by accident.

##### The migration pin, which is the best thing in this round

The v1→v2 migration is `migrate::migrate(&mut bundle, 1)`, 112 lines, and it is reported as a **value**
(`LoadedBundle.migrations`) rather than a §14 `Finding` — *a migrated bundle is older, not inconsistent*,
which is the right distinction and the opposite of what a reflexive implementation would have done.

And it is pinned in the strongest available way: **`saving_the_v1_fixture_produces_the_v2_fixture_byte_for_byte`.**
The v1 fixture is unchanged (`git diff` empty, tree hash recorded); loading it under v2 code gives every
panel `false` and reports exactly one migration; and **saving it reproduces the v2 fixture byte for byte**,
which is itself pinned by a save/reload round trip and a second-save fixed point. That is a migration
proved by an identity rather than by assertions about its parts.

The v2 fixture is **derived, never hand-edited**, with the generator named in its header as an
`#[ignore]`d test — so the next person can regenerate rather than guess.

**Fields deliberately NOT added**, listed rather than left implicit: a lock reason or actor, `locked` on
`Page` or `Lettering`, a persisted **selection** (M6 session state), a `Node.locked` mirror, and §8.1's
importance/fixed geometry.

### M2-L4 — the M2-L3 fix replaced one wrong claim with a narrower one

```
the_message_never_rules_out_craft_fonts_for_a_family_craft_fonts_carries   FAILED

   … BIZ UDMincho is not one of ADR-017's comic faces (Comic Neue, Bangers), so craft-fonts is not
   where it belongs"
```

**I confirmed this myself**: `craft-fonts`'s manifest carries **seven** families —

`Bangers`, `BIZ UDMincho`, `BIZ UD PGothic`, `Comic Neue`, `Noto Sans Arabic`, `Noto Sans CJK SC`, `Shippori Mincho`

— and `is_comic_family` recognises **two** (ADR-017's Comic Neue and Bangers). So for **five of the seven**,
the message tells the creator that **craft-fonts is not where their font belongs**, when craft-fonts is
exactly where it is and `CRAFT_FONTS_DIR` is exactly how it reaches a build.

**The shape is what to record:** the pre-M2-L3 message said *"CRAFT_FONTS being empty is why they are looked

### M2-L5 (withdrawn) — the original candidate, kept for the record

```
a_move_re_bases_the_tail_on_the_translated_edited_path_and_never_on_the_kinds_own_shape   FAILED
  "the base is (-30.5718, 566.2659), and the nearest point of the rectangle the path sits at (-23.0789, 540.0)"
```

The test's expectation is `clamp(tip, moved.bounds)` — the nearest point in the **filled** rectangle. But a
balloon tail's base is plausibly **not** a nearest point: it is likely where the tail's **direction** meets
the outline. Those two coincide for some geometries only. So there are two explanations implying **opposite
verdicts** — the implementation re-based on something other than the path (a defect), or the test's
geometry is wrong (a wrong test) — **and I am not going to guess.** I have been wrong three times in this
milestone, every time by concluding one step early, so the reviewer inherits the question with both
hypotheses and the instruction to settle it by **making the individual checks run** — notably
`tail.is_attached_to_outline(&moved.frame)`, which **never executed** because line 194 panicked first.

Its probe is named `probe_translation_equivariance`, which suggests the previous reviewer was already
circling a **third** possibility: that the answer drifts under a large translation, which would be the M1
f64-exactness class rather than either of the above.

### M2-T3 — the agent harness terminated four working agents at once, and cost two cycles

Mid-milestone, an ordinary tool call was interrupted with *"the execution of this tool, or a previous tool
was interrupted"*. **Nothing in the repository had failed:**

- the interrupted call was a trivial `python3` edit plus `cargo xtask brands`, and **both had actually
  completed** — the edits are in the file, `brands` exits 0 on re-run;
- no `cargo` or `rustc` processes were left running;
- `target/` intact, disk at 80% with 91 GB free, working directory unchanged.

What had happened was that **all four background agents were gone at once** (`<no background agents>` where
four had been running seconds earlier). That is a process-tree teardown, not a code or build failure — and
the tell is that the repository is *consistent* while the agents are *absent*.

**The cost was two cycles, and the cause was concurrency I chose.** Four agents were running
simultaneously, each invoking `cargo` against the shared target directory, in a workspace whose `target/`
was already ~150 GB. Whether the teardown was memory, a target-lock pile-up or the harness's own limits I
cannot prove — but the *association* is clear, and the mitigation is cheap: **run at most two agents at a
time for this repository**, and treat a simultaneous multi-agent disappearance as a capacity signal rather
than a defect.

**It also produced the round's one genuinely useful process change**: because the agents were killed
mid-record, the only surviving evidence of two reviewers' work was their **test files** — and running those
files recovered findings that would otherwise have been lost silently, including a defect introduced by the
fix for a previous one. That is why §8's table now says *land the tests before you write the record*, and
why the instruction is in `.github/instructions/implementation-review.instructions.md` rather than only in
this record.
